1. ラッパーとは

ラッパー(wrapper)＝包み紙。すでにある道具を中に包み、別の使い方ができるようにした薄い層のこと。中身の仕事は自分ではせず、内部で元の道具を呼ぶだけ。

Python でのたとえ

ラッパー包まれているもの何が楽になるか
requestsurllib(標準ライブラリ)HTTP 通信を短く書ける
pandas.read_sqlDB ドライバ(psycopg2 など)結果を DataFrame で受け取れる

React Leaflet の場合

あなたのコード
   │  <Marker position=...> のように「宣言」する
   ▼
react-leaflet   ← ラッパー(React の書き方 ⇔ Leaflet の呼び出しの翻訳役)
   │  内部で L.marker(...).addTo(map) を実行
   ▼
leaflet         ← 本体(実際に地図を描く)
事実package.json の dependencies に leaflet と react-leaflet の両方が入っている。ラッパーは本体がないと動かないので、両方必要。

解釈「薄い」というのは、地図を描く機能を新しく作っているわけではなく、翻訳しているだけ、という意味。

2. 地図のデータ形式と Supabase

まず区別: 地図の絵とデータは別物

種類中身このアプリでは
背景地図画像タイル(道路・地形の絵)CARTO のサーバーから都度取得。自分では保存しない
地理データ座標＋名前などの属性自前で保存する対象

「地図の要素」にあたるのは、下の地理データ。

形式: GeoJSON(現在使っているもの)

事実public/data/stations.geojson の中身(抜粋)。

{
  "type": "Feature",
  "properties": { "kind": "tra", "name": "桃園", "nameEn": "Taoyuan" },
  "geometry":   { "type": "Point", "coordinates": [121.31378, 24.98873] }
}
  • geometry＝形。Point(点)、LineString(線)など。
  • properties＝自由な属性(テーブルの列にあたる)。
  • 座標の順番は [経度, 緯度]。Leaflet の position は [緯度, 経度] で逆。混乱しやすい点。

型は src/types/railway.ts に Stations = FeatureCollection<Point, StationProps> として定義されている(事実)。データ分析の感覚では、GeoJSON は「geometry 列付きの行を並べた JSON 形式のテーブル」。

Supabase との関係

データ保存先状態
鉄道路線・駅GeoJSON ファイル(リポジトリ内 public/data/)事実実装済み
旅行のスポット(ユーザーが登録)Supabase(PostgreSQL)未確認「予定」。package.json に Supabase のライブラリはまだない

つまり「地図の要素＝全部 Supabase」ではない。変わらない大量データ(鉄道)はファイル、増減するユーザーデータ(スポット)は DB、という使い分け。

未確認スポット表の設計は未決定。候補は2つ。
  • A: lat, lng を数値列で持つ(単純。Leaflet にそのまま渡せる)
  • B: PostGIS の geometry 型(「半径◯km 以内」のような空間検索ができる)
ピンを立てるだけなら A で足りる。空間検索が必要になったら B を検討する、が自然な順序。

3. 「データから画面が決まる」

2つの書き方

命令的(素の Leaflet)宣言的(React)
考え方「どう変更するか」の手順を書く「今のデータなら画面はこうなる」を書く
例ピンを1本追加→1本削除→…スポットの配列を渡す。ピンは結果として決まる
SQL でのたとえUPDATE/INSERT を順に実行SELECT(欲しい結果の定義)

解釈式で書くと 画面 = f(データ)。同じデータなら必ず同じ画面になるので、バグの原因を追うとき「データが正しいか」だけ見ればよい。

このプロジェクトでの実例

事実src/hooks/useGeoJson.ts と src/components/RailwayLayer.tsx の流れ。

① 最初:   data = null          → RailwayLayer は null を返す(何も描かない)
② fetch が完了 → setData(json)  ← データ(state)を更新するだけ
③ React が RailwayLayer を再実行 → data がある → <GeoJSON data=... /> を描く

コード中に「線を描け」という命令はない。state(状態)を更新したら、React が画面を作り直す。これが「データから画面が決まる」の中身。

用語意味この例では
stateコンポーネントが持つ、変わりうるデータuseState の data
props親から子へ渡す入力<GeoJSON data=... style=... /> の data など

判断の基準: 「時間とともに変わり、変わったら画面も変わるもの」は state、「親が決めて渡すもの」は props。

4. key の役割

map で同じ部品を並べるとき、React は「どの部品がどのデータに対応するか」を覚えておく必要がある。その名札が key。

{spots.map(spot => (
  <Marker key={spot.id} position={[spot.lat, spot.lng]} />
))}

SQL でのたとえ

key は主キーと同じ発想。行(要素)を同一人物として追跡するための、変わらない一意の値。

なぜ必要か

スポットが [A, B, C] から A を削除して [B, C] になったとき:

keyReact の判断
spot.id(A,B,C の id)「A のピンが消えた。B と C はそのまま」→ 正しい
配列の添字(0,1,2)「0番が B に変わり、1番が C に変わり、2番が消えた」と解釈 → 余計な更新や、部品内部の状態(開いたポップアップなど)が別のスポットに引き継がれる不具合の原因

ルール: 変わらず、重複しない値(DB の id など)を使う。添字は並びが変わらないリストの場合のみ。

事実今のコードの RailMap.tsx / RailwayLayer.tsx には map による並べ描きがなく、<GeoJSON> 1つに全データを渡している。key はスポット機能(Supabase 連携)を作るときに初めて出てくる見込み。

5. ディレクトリ構成

事実my_travel_app/ の実際の構成。(作業ディレクトリの Taiwan_travel_app/ は、index.html と spots.js だけの旧版で別物。)

my_travel_app/
├─ index.html          ← 入口のHTML。<div id="root"> があるだけ
├─ package.json        ← 使うライブラリとコマンド一覧(Pythonの requirements.txt + Makefile)
├─ vite.config.ts      ← ビルド/開発サーバーの設定
├─ tsconfig*.json      ← TypeScript の設定
├─ CLAUDE.md           ← Claude 向けのプロジェクトルール
├─ docs/               ← decisions.md(判断記録)、learning_log.md
├─ scripts/
│   └─ fetch-railways.ts   ← OSMから鉄道データを取得し GeoJSON を作る(1回だけ実行)
├─ public/data/        ← railways.geojson / stations.geojson(そのまま配信される)
├─ src/                ← アプリ本体のソース
│   ├─ main.tsx            ← 起動点。<App /> を root に載せる
│   ├─ App.tsx             ← 画面全体(地図＋凡例)
│   ├─ components/         ← 画面の部品
│   │    ├─ RailMap.tsx        地図の枠と背景
│   │    ├─ RailwayLayer.tsx   路線の線
│   │    ├─ StationLayer.tsx   駅の点
│   │    └─ RailLegend.tsx     凡例
│   ├─ hooks/useGeoJson.ts ← 「GeoJSONを読み込む」処理の部品化
│   ├─ railStyle.ts        ← 路線の種類ごとの色・太さ
│   └─ types/railway.ts    ← 型定義
├─ dist/               ← ビルド結果(自動生成。手で触らない)
└─ node_modules/       ← インストール済みライブラリ(自動生成。手で触らない)

解釈読む順番のおすすめ: main.tsx → App.tsx → RailMap.tsx → RailwayLayer.tsx → useGeoJson.ts。上から下へ「呼び出す側→呼ばれる側」の順に並んでいる。

6. 依存関係

コードの呼び出し関係(import)

index.html
  └ main.tsx
      └ App.tsx
          ├ RailMap.tsx ── react-leaflet(MapContainer, TileLayer)
          │    ├ RailwayLayer.tsx ─┬ useGeoJson.ts ─→ fetch('data/railways.geojson')
          │    │                   ├ railStyle.ts
          │    │                   └ types/railway.ts
          │    └ StationLayer.tsx
          └ RailLegend.tsx

データの流れ

【事前に1回】 OSM(Overpass API) → scripts/fetch-railways.ts → public/data/*.geojson
【実行時】     ブラウザ → useGeoJson が fetch → state → 地図に描画
【背景地図】   ブラウザ → CARTO のタイルサーバー(都度取得)

外部ライブラリ(package.json)

区分パッケージ役割

(動くのに必要)		react / react-dom画面の仕組み本体 / ブラウザへの描画
